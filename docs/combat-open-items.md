# 战斗系统三处未决问题

状态：2026-11-26 记录。除注释修正外**没有改代码**——三条都会动到表现层契约或弹道规则，
需要先对齐口径再落地。

读法：每条按「现状（代码事实）→ 为什么是问题 → 待定/已定 → 落地判据」写。
第 1、2.2 节是 HUD 接入前必须先对齐的约定，第 3 节会改弹道规则，第 2.1 节属于 Phase 1.5。

---

## 1. 就位状态与实际开火结果必须分开表达

### 1.1 现状

- `TurretSnapshot.CanFire = 装填完 && HasAim && InArc`，**不含能源**。
- 能源在开火那一刻才判。`PowerSystem.TryConsumeShot` 扣不出电就 `break`：本舰后续炮座全都不打，
  发一条 `PowerLow`（同一状态连续出现只报一次，避免 AI 每 tick 重提开火把事件刷满）。
- 因此 `CanFire == true` 的炮座**可能一发都没出**；同一轮里也可能前几门打出去、后面几门卡在能源上。
- `CanFire` 从不回写状态，`Fire` 事件是唯一出弹路径——代码层面已经满足"开火只由事件驱动"。

### 1.2 问题

"具备条件"和"已经开火"是两个信号，但 `CanFire` 这个名字读起来像后者。
一旦表现层写成 `if (turret.CanFire) 播炮口火焰`，断电那一轮就会看到一排炮口闪光、弹丸却一颗没有。

### 1.3 约定（HUD 接入时照此实现）

| 信号 | 含义 | 谁产生 | 频次 |
| --- | --- | --- | --- |
| `CanFire` | 这一门**有资格**出弹（装填完 + 有解 + 在界内） | 快照 | 每 tick |
| `Fire` | 这一门**真的**出弹了 | 事件，带 `Shot` 载荷 | 开火瞬间 |
| `PowerLow` | 有炮座因能源不足未能开火 | 事件，去重 | 状态变化时 |
| `NotReady` / `OutOfArc` | 全部在装填 / 全部出界 | 事件，去重 | 状态变化时 |

四条硬规矩：

1. 就位状态只用来高亮"哪些炮现在满足条件"，不得当"已开火"用。
2. 炮口火焰、后坐动画、弹丸生成，一律由 `Fire` 事件触发。
3. 能源不足单独提示，不要混进"在冷却"或"出界"——玩家要能分清是等 CD、转船，还是断电。
4. 部分炮座开火、其余因能源不足未开火，是**合法状态**，不是异常。

### 1.4 为什么本轮只"保留接口"

代码不需要改：`Fire` 已经是唯一出弹路径，`CanFire` 只读。缺的是把话说清楚，
所以这轮只改了 `CanFire` / `TurretsInArc` 的注释，明确写出"不含能源、不要据此推断已开火"。

如果将来嫌名字有歧义，可考虑改叫 `LoadedAndInArc`——但那要动契约字段名，等 HUD 真正接入时一起做，
避免现在改一次、接入时再改一次。

### 1.5 落地判据

- 断电轮次：已开火的炮有炮口效果，未开火的只有能源不足提示，两者不串。
- 断点检查：表现层里出现 `if (CanFire)` 后面跟着特效/音效，即判为错。
- `Fire` 事件条数 == 同一 tick 新生成弹丸数（现在天然成立，接 HUD 时不要打破）。

## 2. 炮塔类型，与装填时长的生效规则

这是**两个独立问题**，只是都落在"炮塔"这一个数据结构上，所以写在同一节：
2.1 是"炮塔可以有几种、怎么配"，2.2 是"装填计时怎么算"。后者与炮塔类型无关，全动能炮也会发生。

### 2.1 炮塔类型（待设计，排 Phase 1.5）

**现状**：`TurretProfile` 没有类型字段，唯一区分维度是 `Channel`，而且这一轮刚把它收紧成只允许 `kinetic`。
杀伤效果全走一条实体弹道路径。

三个概念必须分开，否则会互相污染：

| 概念 | 回答什么 | 当前载体 | 状态 |
| --- | --- | --- | --- |
| 炮塔类型 | 用什么投送、能装什么弹、配什么模型动画 | 无 | 待加 |
| 弹药 | 这一发怎么飞（直飞 / 制导 / 持续照射） | 无 | 待加，看是否真需要 |
| 伤害通道 | 打上去怎么结算（读哪条装甲 DR） | `DamageChannel` | 已有，只挑防御分支 |

三种炮塔的候选分工：

| 炮塔类型 | 投送方式 | 需要明确的属性 |
| --- | --- | --- |
| 动能炮塔 | 发射实体弹丸 | 弹速、装填时间、散布（现在这三个都有） |
| 导弹发射装置 | 发射制导弹 | 发射间隔、弹药量、制导能力（过载 / 追踪角速度 / 燃料） |
| 光束炮塔 | 光束投送 | 瞬时还是持续照射、充能、散热 |

**两条设计路径**：

- **A 专用炮塔**：一门炮一种投送，配置、模型、动画一一对应。
- **B 炮塔 + 兼容弹药清单**：一门炮可装动能弹与制导弹，制导行为写在弹丸自身；
  炮塔只负责限制"能装哪几类"。这与"通道负责防御结算"不冲突——类型决定能装什么，弹药决定怎么飞，通道决定怎么算。

**倾向 A，理由**：B 会立刻带出"弹药库存 + 装填时切换弹种 + UI 选择"三件事，
而 Phase 1.5 的目标只是验证通道差异（远距投射体 / 近距光束的收益是否成立）。
等确实出现"同一门炮换弹"的玩法，再把 A 扩成 B，数据结构上是加一个 `ammo[]` 白名单，不会推倒重来。

### 2.2 装填时长：本轮固定（已定方案，未实现）

**现状**：`Reload01 = 1 − 剩余时间 ÷ (ReloadSeconds × ReloadScale)`，而 `ReloadScale` **每 tick**
按当前武器能源份额重算（`1.4 − 0.8 × 武器份额`）。

两版都不完美，值得记一笔：

| 口径 | 好处 | 坏处 |
| --- | --- | --- |
| 分母固定 `ReloadSeconds` | 进度连续，切档不跳 | 导航档下条走满还要再等 16%，"满了打不出" |
| 分母含 `ReloadScale`（现在） | 条满 = 真能打 | 中途切档时分母变，进度跳变，**降档会倒退** |

退化到最小的复现：均衡档打一发（6.8 s），过 3 s 切交战档 → 进度从 0.44 掉到 0.36。
全是动能炮也会发生，与炮塔类型无关。

**约定**（一次开火，本轮总时长就定死）：

- 开火那一刻算一次 `本轮总时长 = ReloadSeconds × 当时的档位系数`，存进 `TurretReloadTotal[t]`。
- 进度条始终用 `剩余时间 ÷ 本轮总时长`，分母不再随 tick 变。
- 能源档位变化**从下一轮装填开始生效**，不追溯调整正在走的那一轮。

为什么不选动态装填：动态会让"还要等多久"随玩家操作跳，而玩家恰恰需要这个数稳定才敢切档。
固定本轮换来的是可预测性——切档的收益从下一发开始，读起来也简单，规则解释成本最低。

**落地要点**：

- `CombatShip` 加 `float[] TurretReloadTotal`，与 `TurretReload` 等长，`ResetTurrets` 一起建。
- 开火处 `TurretReload[t] = TurretReloadTotal[t] = turret.ReloadSeconds × reloadScale`。
- 快照 `Reload01 = 1 − TurretReload[t] ÷ TurretReloadTotal[t]`，分母退化时（≤0）取 1。
- `CombatShip.Reload01`（全舰汇总）同步改成逐座取最大值，口径与明细一致。

**落地判据**（进 SmokeTests）：

- 装填中途来回切三档，`Reload01` 单调不回退，总时长等于开火时那一档。
- 装填走满的时间 = 开火时刻的档位系数 × `ReloadSeconds`，不是当前档位。

## 3. 瞄准方向应等于弹丸的世界运动方向

### 3.1 体验目标（可以直接写进设计稿）

玩家指定的瞄准方向，表示弹丸出膛后**在世界坐标中的初始运动方向**；舰体自身的横向速度，
不应额外造成玩家未预期的弹道偏移。

用"初始"而不是"最终"：制导弹发射后会转向，不可能保持同一个方向。

### 3.2 现状

`Projectile.Vel = 舰速 + 炮口方向 × 弹速`。炮口方向来自 `TryAim`：有锁定就按**相对速度**解提前量，
否则用玩家瞄准点，都没有就沿舰首。

这带来一个分叉：

- **锁定时其实是自洽的**。`TryLeadPoint` 用的就是 `目标速度 − 本舰速度`，已经把舰速算进去了，
  弹会落在预定点上。这也解释了为什么"打不着"的锅不能全甩给舰速。
- **自由瞄准时不自洽**。玩家把准星放在某处，炮口就指向那里，但弹丸继承了舰速，世界运动方向偏向舰速那一侧。
  横移 30 km/s、弹速 220 km/s，夹角约 7.8°；180 km 上偏出约 24 km，而实际散布只有 0.25 km 量级——
  差两个数量级，玩家会觉得"我明明瞄准了"。

### 3.3 两条路线（待决策，不能只改事件字段）

**A 保留舰速继承 + 火控补偿**

- 炮口指向 = `normalize(期望世界方向 × 弹速 − 舰速)`。
- **补偿后的指向必须重判射界**：补偿可能把炮口推出界，于是"看着对准了却打不出去"多出一种成因。
- 好处：物理连贯（太空里炮弹本就继承舰速），追击更快、迎头更慢的差异保留。
- 代价：射界判定挪到补偿之后，判定链变长；HUD 上"能打/不能打"的解释成本上升。

**B 直接规定弹丸的世界初速**

- 弹丸出膛世界速度就是 `炮口方向 × 弹速`，不叠舰速。
- 好处：瞄准与弹道一一对应，HUD 直读，不需要火控补偿。
- 代价：太空牛顿感打折（高速掠过时炮弹"不跟着走"）；追击与迎头的伤害差异消失，
  而那个差异是"高速接近"这套战术的收益来源之一。

倾向在灰盒里各跑一次"横移开火"再定。判据不是数值，而是：**玩家不看数字能不能说出"为什么偏了"**。
A 要求 HUD 把"舰速补偿导致的射界出界"解释清楚，B 要求接受"炮弹不继承舰速"的世界观设定。

### 3.4 无论选哪条都必须满足

1. 无散布时，弹丸世界初速方向与解算后的瞄准方向一致。
2. 有散布时，只允许配置里的散布造成偏差。
3. 开火事件提供**实际世界初速度**，供曳光、拖尾使用（现在是炮口朝向 + 弹速，缺舰速那一项）。
4. 提前量计算、射界判断、弹丸初速生成**走同一套规则**，不能三处各算一遍。

### 3.5 现在开发时的约束（Unity 灰盒阶段）

不要把旧假设写死进表现层：

- 跟踪弹丸用快照里的 `Projectiles` 位置，**不要**用 `Direction × 弹速 × t` 外推。
- 开火表现只消费 `Fire` 事件（与第 1 节同一条规矩）。
- 曳光如果一定要按方向画，只能画很短一段（一两帧）；长拖尾必须跟快照。

### 3.6 本轮已修正的注释

`TurretShot` 原注释写"Direction 已含散布，与 Projectile 的实际初速同源，所以曳光弹可以直接拿它朝画"——
有舰速时这句不成立，正是本节要防的那个假设。已改成"炮口朝向，不是世界运动方向"，
并指向本文档。代码行为未变。
