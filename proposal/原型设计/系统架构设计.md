# 《小兵传奇》星际战争游戏 — 设定梳理与系统架构设计

> 第 1–2 周"设定梳理、原型设计"阶段产出。战斗形态定为实时 3D 的单机遭遇战，操作手感参照《战舰世界》；战略层（星图 / 关系网 / 经济 / 剧情）沿用原设计，不随战斗形态变化。本文用于评估项目规模、确定 MVP 范围。

---

## 一、设定梳理：从小说到游戏

### 1.1 设定到机制的映射

这是整个项目最关键的转化层。小说里每一类设定都要落到具体的游戏对象上，否则就只是背景文字。下表是完整的映射关系：

| 小说设定 | 游戏内对象 | 承载系统 | 数据来源 |
|---|---|---|---|
| 四种政体（民主/帝制/宗族/宗教） | 阵营模板 FactionTemplate | 阵营系统 | 第 5、11 章 |
| 六等二十一级军衔 | 军衔 Rank + 晋升规则 | 成长系统 | 第 7 章 |
| 军功晋升（联邦可作弊/大唐严格） | 功绩值与晋升判定策略 | 成长系统 | 第 83、160 章 |
| A–J 级舰船 + 特种舰 | 舰船 Ship + 舰船模板 | 战斗系统 | 第 34 章数值表 |
| 军种（战机/陆战队/机甲/机器人/舰内兵种） | 兵种 UnitType + 克制矩阵 | 战斗系统 | 第 2、14、61、66 章 |
| 舰队阵型（W/V/圆锥/环形） | 阵型 Formation + 加成 | 战斗系统 | 第 82–85 章 |
| 星系/行政星、空间跳跃、边境屏障 | 星图 StarMap + 移动规则 | 地图系统 | 第 1、5 章 |
| 人格化中央电脑"星零" | AI 副官 AIOfficer | AI 层 | 第 8、12 章 |
| 总统—议会—元帅三角、派系倾轧 | 关系网 RelationGraph | 关系网系统 | 第 21、30 章 |
| 皇子夺嫡、贵族站队 | 关系网（另一套权重配置） | 关系网系统 | 第 13、23 章 |
| 家族分封、资源开采、制造业 | 资源节点 + 生产链 | 经济系统 | 第 90–92 章 |
| 货币（篮金/铂石/武莱币）、税率 | 货币 Resource + 经济参数 | 经济系统 | 第 68、90 章 |
| 四阶段主线矛盾 | 剧情章节 StoryChapter + 触发条件 | 剧情系统 | 故事线分析文档 |

### 1.2 核心玩法循环

游戏分成两层。**战略层**决定"打谁、在哪打、带什么舰"，**战斗层**决定"怎么打"，战斗结果回写战略层。两层用一条窄接口隔开，互不侵入。

```
    ┌──────────── 战略层 ────────────┐
    │  选择阵营 → 接取剧情任务 → 星图机动  │
    │  关系网博弈 / 资源调度 / 舰队编成    │
    └──────────────┬───────────────────┘
                   │ 进入战斗：敌我编成 + 战场类型 + 剧情目标
                   ▼
    ┌──────────── 战斗层（实时 3D） ────────────┐
    │  操舵机动 → 瞄准预判 → 弹道飞行 → 命中判定   │
    │  分队指令 / 星零实时提示 / 战场环境利用      │
    └──────────────┬───────────────────────────┘
                   │ 退出战斗：战损 + 军功 + 耗时 + 剧情标记
                   ▼
    ┌──────────── 回写战略层 ────────────┐
    │  军功→晋升→更大舰队；战损→补给消耗      │
    │  战斗结果→剧情分支；关系变化→政治事件   │
    └────────────────────────────────────┘
```

**关键设计约束**：前期联邦/银鹰玩家不接触资源调度（由高层代管），家族玩家从一开始就接触完整经济。但两者用的是同一套经济系统，只是 UI 是否暴露、初始资源是否给定的区别。这是"三阵营共享一套代码"的技术前提，与战斗层无关。

### 1.3 三阵营差异化配置

用配置数据驱动差异，而不是写三套逻辑。每个阵营是一份配置表：

| 维度 | 联邦 | 银鹰帝国 | 家族 |
|---|---|---|---|
| 成长货币 | 军功 | 军功 | 资源/领地 |
| 前期资源可见度 | 仅弹药与舰船配置 | 仅弹药与舰船配置 | 全部 |
| 关系网初始形态 | 高猜疑、派系林立 | 高忠诚、夺嫡站队 | 简单、家族内部 |
| 关系网可用操作 | 拉拢/举报/冒功 | 站队/联姻/清洗 | 任免/分封 |
| 起始位置 | 首都星系 | 帝都星系 | 无乱星系边缘 |
| 剧情线 | 唐龙视角 | 帝国视角 | 沙盒 |
| 核心张力 | 功高震主 | 皇子夺嫡 | 资源与扩张 |

三阵营的战斗层完全共用：舰船参数、弹道、分队指令、敌舰 AI 都是同一套，差异只体现在"带什么舰进战场"（由成长结果决定）。

### 1.4 战斗群映射：从《战舰世界》的舰船子系统到小说设定

这是战斗设计的核心。《战舰世界》里玩家驾驶的"一艘舰"本身就是一套战斗群——主炮、副炮、侦察机、舰载机各司其职。这套结构可以直接映射到小说的舰队设定，把 RTS 的指挥复杂度压缩进"开一艘船"的操作里。

| 战舰世界的子系统 | 功能 | 小说对应设定 | 游戏内角色 |
|---|---|---|---|
| 主炮塔 | 玩家手动瞄准的主力输出 | 主舰主炮（第 34 章主炮数值） | 玩家直接驾驶的**主舰** |
| 副炮 | 自动攻击近距离目标 | 僚舰 / 护航舰 | **僚机分队**：自动索敌，可指派目标 |
| 水上侦察机 | 前出点亮、提供视野 | A 级巡逻艇（第 34 章） | **巡逻分队**：前出侦察，点亮敌舰 |
| 舰载机编队 | 可派出的空中攻击力量 | 副舰 / 舰载战机 | **副舰分队**：按指令出击，有冷却 |
| 舰体航行与装甲 | 移动、受击、沉没 | 巡洋舰 / 战列舰级主舰 | 玩家操舵对象，有转向半径与速度档 |

由此得到四个固定分队槽位：**主舰（玩家）+ 僚机 + 巡逻 + 副舰**。每方最多 4 支分队（规模可调），玩家只直接操控主舰，其余三支通过"跟随 / 攻击指定目标 / 前出侦察 / 撤回"四类指令调度。这样既有舰队作战的层次感，又不用做逐艘操控的 RTS。

**小说数值的用法**：第 34 章那张 A–J 级舰船表（乘员 / 主炮 / 副炮 / 发射口 / 防御度）是属性底子，但要补齐小说没给的战斗参数——航速、转向半径、主炮射程、炮弹初速、装填时间、装甲厚度、血量。这部分是自己设计的，需要在原型阶段用实际手感来调，不能照抄。

### 1.5 战斗规模与舞台

- **规模**：每方最多 4 支分队，单支分队 1–3 艘舰；玩家直接驾驶主舰，其余为 AI 友军。
- **舞台**：一片有限空域，边界由剧情限定（例如"边境屏障"），不做无缝开放宇宙。
- **舰体表现**：所有舰体套用同一套 3D 模型，靠涂装、比例缩放、挂载武器区分舰种。自己做精细舰模对课程项目没有必要，省下的时间投到环境和手感上。
- **环境渲染重点**（体现星空特点）：
  - 恒星：发光球体 + 点光源 + 光晕，决定场景主光的方向和色调
  - 小行星带：程序化生成的低模石块群，可作掩体（遮挡弹道与视线）
  - 零散陨石：背景装饰，少量带缓慢运动
  - 星空背景：天空盒 + 星点粒子
  - 特效：尾焰、炮口焰、命中火花、舰体倾斜下沉

环境用程序化生成 + 现成免费资产，不做手工建模，这是把美术成本压住的关键。

## 二、系统架构

### 2.1 分层架构

沿用四层结构，核心原则仍是**逻辑与表现分离**。实时战斗更需要这条原则：战斗仿真逻辑不依赖 Unity 的 MonoBehaviour，用固定步长（fixed timestep）推进，渲染层只读取仿真状态。否则帧率一变，弹道和命中判定就跟着变，调试会变成灾难。

```
┌─────────────────────────────────────────────────────┐
│  表现层 Presentation (Unity)                        │
│  战略UI · 关系网UI · 资源面板 · 剧情对话框            │
│  3D 战斗场景：舰船/环境/相机/特效/HUD                 │
└──────────────────────┬──────────────────────────────┘
                       │ 事件订阅 / 命令下发 / 状态读取
┌──────────────────────▼──────────────────────────────┐
│  应用层 Application — 游戏流程编排                   │
│  GameSession · 任务调度 · 存档/读档 · 阵营配置加载    │
│  BattleSession（战斗生命周期：进入/更新/结算/退出）    │
└──────────────────────┬──────────────────────────────┘
                       │ 调用领域服务
┌──────────────────────▼──────────────────────────────┐
│  领域层 Core (纯C#，无Unity依赖)                     │
│  ┌────────┬────────┬────────┬────────┬────────┐      │
│  │关系网  │战斗仿真│地图    │经济    │剧情    │      │
│  │Relation│Battle  │StarMap │Economy │Story   │      │
│  └────────┴────────┴────────┴────────┴────────┘      │
│  战斗仿真内部：运动学 · 弹道 · 命中 · 分队 · 敌舰决策  │
│  ┌────────────────────┬────────────────────────┐     │
│  │成长 Progression    │AI副官 AIOfficer        │     │
│  └────────────────────┴────────────────────────┘     │
└──────────────────────┬──────────────────────────────┘
                       │ 读取配置数据
┌──────────────────────▼──────────────────────────────┐
│  数据层 Data                                        │
│  舰船表 · 弹道参数表 · 军衔表 · 阵营配置 · 剧情脚本    │
│  （ScriptableObject / JSON / CSV）                   │
└─────────────────────────────────────────────────────┘
```

### 2.2 模块职责与依赖

| 模块 | 职责 | 依赖 | 被依赖 |
|---|---|---|---|
| Relation 关系网 | 维护人物/派系节点与关系边；判定忠诚、猜疑、背叛事件 | 剧情、经济 | 剧情、UI |
| Battle 战斗仿真 | **固定步长推进的战场仿真**：运动、瞄准、弹道、命中、战损 | 数据（舰船/弹道表）、成长 | 剧情、UI、AI |
| FleetCommand 分队 | 4 个分队槽位的状态机；执行玩家指令与 AI 友军行为 | 战斗仿真、数据 | 战斗仿真、UI |
| EnemyAI 敌舰决策 | 敌舰的路径选择、目标选择、开火时机（脚本化行为） | 战斗仿真、地图 | 战斗仿真 |
| StarMap 地图 | 星系图、移动规则、跳跃与屏障、补给线 | 数据 | 战斗、经济、UI |
| Economy 经济 | 资源产出与消耗、生产链、税率、贸易 | 地图、数据 | 关系、成长、UI |
| Story 剧情 | 章节推进、分歧判定、事件触发、结局 | 关系、战斗、经济（读状态） | UI、应用 |
| Growth 成长 | 军功累计、晋升判定、解锁 | 战斗（战功）、经济 | 战斗、UI |
| AI 副官 | 战略层情报建议 + 战斗层实时战术提示 | 战斗、地图、关系（只读） | UI |

**依赖原则**：Story 是唯一读取所有其他模块状态的"上层裁判"；AI 副官只读不写；战斗仿真不直接调用经济或剧情，只通过 `BattleSession` 回传结果。这条边界是范围失控时能否收缩的关键——战斗模块可以独立砍功能，不影响战略层。

### 2.3 核心数据结构

```csharp
// 阵营配置：一份配置驱动一个阵营，新增阵营=新增配置
public class FactionConfig {
    public string Id;                    // "federation" / "empire" / "clan"
    public GrowthMode Growth;            // Merit 或 Resource
    public ResourceVisibility Visibility;
    public RelationPreset Relation;
    public StoryRoute Route;
    public Vector2 StartNode;
}

// 舰船：基础属性来自小说第34章，战斗参数需自行补齐
public class Ship {
    public ShipClass Class;              // A..J + Special
    public int Crew, MainGun, SubGun, Torpedo, Defense;  // 小说原值
    public float MaxSpeed, TurnRate;     // 自定：航速、转向
    public float GunRange, ShellVelocity, ReloadTime;    // 自定：射程/初速/装填
    public ArmorProfile Armor;           // 自定：核心区/非核心区两档

// 战斗会话：战略层与战斗层之间唯一的窄接口

}
```

### 2.4 关键接口

回合制时代的 `Resolve()` 一次性结算接口作废，换成战斗场景的生命周期接口：

```csharp
public interface IBattleSession {
    void Initialize(BattleConfig config);   // 战略层 → 战斗层
    void Step(float fixedDelta);            // 每帧推进仿真（固定步长）
    void IssueOrder(SquadRole role, SquadOrder order, Ship target);
    void SetAim(Vector3 worldPoint);        // 玩家瞄准输入
    void SetHelm(float throttle, float rudder); // 操舵输入
    BattleResult Finalize();                // 战斗层 → 战略层
}

public interface IRelationService {
    void Adjust(string from, string to, RelationType type, int delta);
    bool WillBetray(string characterId);
}
public interface IStoryEngine {
    void OnEvent(GameEvent e);
    StoryNode GetCurrentNode();
    void Choose(int optionId);
}
public interface IAIOfficer {
    StrategicAdvice Suggest(BattleBrief brief);      // 战略层：战前建议
    TacticalHint Tick(BattleSnapshot snap);          // 战斗层：实时提示
    string Answer(string question);                  // 剧情对话（可接 LLM）
}
```

### 2.5 事件流

```
战略层：玩家操作 → UI 发 Command → Application 调用模块
       → 模块改状态并抛 GameEvent → StoryEngine 判定剧情分支 → UI 刷新

进入战斗：Application 创建 BattleSession(config)，切换到 3D 场景

战斗中（每帧）：
       玩家输入（操舵/瞄准/分队指令） → BattleSession.Step(dt)
       → 运动学更新 → 弹道推进 → 命中判定 → 状态变更
       → 表现层读状态渲染（相机/舰船/特效/HUD）
       → AIOfficer.Tick 读快照，输出实时提示（去抖后显示）

退出战斗：BattleSession.Finalize() → 结果回传 → 经济扣补给、成长加军功、
       Story 记录剧情标记 → 切回战略层
```

## 三、复杂度评估

### 3.1 模块复杂度矩阵

按"数据准备 / 规则逻辑 / UI 表现 / 外部依赖"四维打分，给出 3 人 12 周工期下的人天估计。实时战斗拆得比上一版细，因为原来的"战斗系统 12–18 人天"是把运动、敌舰 AI、分队指挥笼统算在一起的粗估。

| 模块 | 数据准备 | 规则逻辑 | UI 表现 | 外部依赖 | 人天 | 风险 |
|---|---|---|---|---|---|---|
| 数据层（舰船/弹道/军衔/星图） | 中 | 低 | — | 无 | 4–5 | 低 |
| 战斗仿真（运动/瞄准/弹道/命中） | 中 | **高** | 中 | 无 | 22–30 | **高** |
| 分队系统（4 槽位 + 4 类指令） | 中 | 中 | 中 | 无 | 8–12 | 中 |
| 敌舰 AI（脚本化行为） | 低 | **高** | 低 | 无 | 8–12 | **高** |
| 星空环境渲染 | 中 | 低 | **高** | 免费资产 | 8–12 | 中 |
| 舰体模型与战斗特效（共用模型） | 低 | 低 | 中 | Blender | 6–10 | 中 |
| 战斗 HUD | 低 | 中 | **高** | 无 | 6–9 | 中 |
| 关系网 | 中 | 中 | **高** | 无 | 8–12 | 中 |
| 地图 StarMap | 中 | 中 | 中 | 无 | 6–9 | 中 |
| 经济 Economy | 中 | 中 | 低 | 无 | 5–7 | 低 |
| 剧情 Story | **高** | 中 | 中 | 无 | 10–14 | **高** |
| 成长 Growth | 低 | 低 | 低 | 无 | 2–3 | 低 |
| AI 副官 | 低 | 中 | 低 | LLM 可选 | 5–8 | 中 |
| UI 整合 | — | — | 高 | — | 8–12 | 中 |
| **合计（完整版）** | | | | | **106–162 人天** | |

3 人 × 12 周 ≈ 180 人天理论容量，扣除课程与沟通损耗约剩 120–150 人天。**完整版卡在容量上限，没有余量，必须砍范围。**把敌舰 AI 做成纯脚本、环境用程序化生成、装甲只做两档之后，MVP 版可压到 **85–115 人天**，留出返工空间。

### 3.2 三个真正的难点

**难点一：实时战斗的手感（最硬核）。** 难不在"画一艘船在动"，而在弹道与命中的调试：炮弹飞行时间、下坠、散布圈要让"打移动目标需要预判"这件事成立，同时不能难到没人打得中。装甲判定如果做完整跳弹角度计算，调试量会翻倍；建议只做"核心区 / 非核心区"两档伤害倍率，跳弹用简化角度判定。这部分要用实际操玩来调，不能靠纸面数值。

**难点二：敌舰 AI。** 单机没有真人对抗，战斗有没有意思全看 AI 像不像回事。好消息是剧情遭遇战不需要通用 AI——每种敌人给一套脚本化行为（巡逻航线、发现玩家后接近、保持距离齐射、血量低时撤退）就够了。别做动态战术决策，那是最容易失控的地方。

**难点三：剧情脚本量。** 四阶段主线 + 三阵营视角 + 分歧点，写下来是几十个剧情节点、上百段对话。这部分不考验技术，考验人力。小说原文可以直接改编，但要改造成"带触发条件和分支的结构化脚本"。MVP 只做一条阵营线的前两个章节。

### 3.3 AI 部分的取舍

AI 副官现在有两个落点，比回合制版本更自然：

| 场景 | 做法 | 人天 | 评价 |
|---|---|---|---|
| 战略层战前建议 | 规则式：根据敌我编成推荐带上什么舰 | 3–4 | **MVP 必做**，稳定可控 |
| 战斗层实时提示 | "敌舰主炮装填完毕，建议转向"；命中时提示"击穿核心区" | 2–4 | **加分项**，实时性要求高，规则式先做 |
| 剧情对话 | 接 LLM，星零回答问题 | 3–5 | 演示效果好，但有延迟与不确定性，放最后 |

实时提示对延迟敏感，绝不能走 LLM 同步调用。建议前两个用规则式，LLM 只放在剧情对话。保留 `IAIOfficer` 接口，后期可无痛替换。

### 3.4 MVP 范围建议

**第一优先级（必须做）**：
- 一个阵营（联邦）从剧情任务 → 星图机动 → 进入战斗 → 回写结果的完整闭环，覆盖前两个剧情章节
- 实时战斗：玩家操舵 + 主炮瞄准 + 弹道预判 + 两档装甲命中；1 种玩家舰 + 2 种敌舰
- 4 个分队槽位，但只实现"跟随 / 攻击目标"两条指令
- 敌舰脚本化行为 2 套，小规模遭遇战（每方 2–3 艘）
- 星空环境：恒星 + 小行星带 + 星空背景（共用舰模，特效先简单）
- 关系网列表版（表格）

**第二优先级（有余力做）**：
- 银鹰、家族阵营配置接入（验证"配置驱动差异"的架构）★ 验证共享架构价值的关键实验
- 巡逻/副舰分队的侦察与出击指令
- 更丰富的环境：陨石运动、命中特效、舰体倾斜下沉
- 关系网图形版、经济完整生产链

**明确不做**：航母舰载机复杂度、完整跳弹角度计算、多舰种平衡、动态战术 AI、全四阶段剧情、联网对战。

### 3.5 架构上的最大风险

**风险一：战斗层与战略层的边界守不住。** 实时战斗很容易吸走全部精力，最后剧情、关系网、经济变成空壳，`BattleSession` 的窄接口也就形同虚设。防线是：先做出"剧情 → 战斗 → 回写"的最小闭环，再打磨战斗细节；不要在闭环打通之前调弹道手感。

**风险二："三阵营共享"是双刃剑。** 联邦/银鹰的"资源由高层代管"和家族的"资源全面可见"，如果实现成两套 UI 逻辑，共享就失效了。正确做法是同一套经济系统 + `ResourceVisibility` 配置控制 UI 显示。战斗层反而是共享最容易守住的部分——三阵营用同一套战斗代码，差异只在带什么舰进场。

## 四、原型设计说明

配套的可点击原型（`prototype.html`）用于验证四件事：
1. **战略层信息架构**：剧情/关系/资源/星图四块信息放在一屏是否合理
2. **战斗 HUD 的信息密度**：操舵、瞄准、弹道预判、4 个分队状态、敌舰列表、星零提示同时呈现是否过载
3. **阵营差异呈现**：切换阵营后，哪些 UI 显示/隐藏，玩家能否理解差异
4. **交互流程**：从接任务 → 星图机动 → 进入战斗 → 战斗反馈 → 回写结算 → 晋升的闭环是否顺畅

原型是静态模拟，只演示交互与信息展示，不接真实规则引擎，也不做真正的 3D 渲染。它是"看得见的架构"，帮助判断每个模块要承载多少信息量，以及实时战斗的 HUD 会不会把屏幕塞满。
